# self-review

PR の差分を多角的・厳格にセルフレビューする。修正は行わず、問題点の列挙と改善案の提示のみ行う。

## 引数

- `$ARGUMENTS` — 追加で重点的に見たい観点（省略可）

## 手順

1. **PR 情報と差分を取得する**
   - `gh pr view` で PR のタイトル・説明・番号を確認する
   - `gh pr diff` で差分全体を取得する
   - 関連ファイルが必要なら Read ツールで読む
   - これらは並列で取得する

2. **以下の観点で厳格にレビューする**

   ### 正確性・バグ
   - ロジックに誤りはないか（境界値・ゼロ・空リスト・None など）
   - 条件分岐に漏れはないか
   - 型の扱いに誤りはないか（型キャスト、Optional の扱いなど）
   - 副作用のある処理が意図せず複数回実行されないか

   ### 設計・構造
   - 責務が適切に分離されているか（1関数1責務）
   - 同じロジックの重複（DRY 違反）はないか
   - 継承・Mixin・Composition の選択は適切か
   - 将来の拡張を想定した不要な抽象化をしていないか（YAGNI）
   - 既存の類似クラス・関数と設計上の一貫性があるか

   ### コーディングスタイル（AGENTS.md 準拠）
   - 命名：省略しすぎ・長すぎ・役割が不明瞭な名前がないか
   - 簡潔さ：不要な中間変数・過剰な分岐・冗長な early return がないか
   - コメント：不要なコメント（自明な説明）が混入していないか。WHY コメントのみ許容
   - 静的型付け：型ヒントの漏れ・`Any` の多用がないか
   - private method の乱立・再利用しない小関数への過剰分割がないか

   ### テスト
   - 追加・変更したロジックに対応するテストがあるか
   - 正常系だけでなく異常系・境界値がカバーされているか
   - テストの粒度は適切か（過剰に細かい / まとめすぎ）
   - テストのアサーションが意味のある値を検証しているか
   - モックの使いすぎで実際の挙動を検証できていないケースがないか

   ### 一貫性・網羅性
   - 既存の類似クラスで行われている処理が今回の変更で漏れていないか
   - 追加したクラス・メソッドに対応するレジストリ登録・import・export が揃っているか
   - エラーメッセージの文体・言語（英語/日本語）がプロジェクトの慣習と一致しているか

   ### セキュリティ・安全性
   - ユーザー入力・外部入力のバリデーションが適切か
   - global / class 変数に意図せず機密情報が保持されないか
   - 例外の握りつぶし（`except Exception: pass`）がないか

   ### ドキュメント・可読性
   - PR の説明が変更内容を適切に説明しているか
   - 複雑な設計判断にコメントが付いているか（付けすぎは NG）

   ### 引数で追加指定された観点
   - `$ARGUMENTS` が指定されている場合、その観点を上記に加えて重点的に確認する

3. **結果を出力する**

   以下のフォーマットで出力する。問題がない観点は省略してよい。

   ```
   ## セルフレビュー結果

   ### 🔴 要対応（マージ前に直すべき）
   - [ファイル:行] 問題の説明 → 改善案

   ### 🟡 要検討（議論の余地あり）
   - [ファイル:行] 問題の説明 → 改善案

   ### 🔵 軽微・提案（余裕があれば）
   - [ファイル:行] 問題の説明 → 改善案

   ### ✅ 問題なし
   特に指摘なし / または問題なしの観点を列挙
   ```

## 注意

- 修正は行わない。指摘と改善案の提示のみ
- 既存コード（変更していない箇所）への指摘は原則しない。ただし今回の変更が既存コードとの不整合を生む場合は指摘する
- 「かもしれない」レベルの推測指摘は 🔵 に分類する
- 指摘がゼロでも「問題なし」と明示する（レビューしていないと混同しないよう）
