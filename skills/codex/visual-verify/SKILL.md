# /visual-verify — UI・生成物目視確認スキル

実装完了前確認のステップ3。ユーザーがデバッグ環境を起動する手間をなくし、
AIが撮った証拠（スクリーンショット・GIF・出力サマリー）を見るだけで実装の正否がわかる状態を作る。

**失敗したらサイクルを回す**: 確認してNGなら修正→再確認を繰り返す。「NG でした」で終わらない。

## 利用者テストとの境界

スクリーンショットやGIFは、表示、clipping、文字、情報密度、静的な前後状態を確認する補助証拠である。クリック数、手動のwindow/tab切替数、scroll回数、自動遷移の原因、focus・前面window、所要時間は画像から推測しない。これらが要件なら `design-user-tests` で実装前にjourneyへ固定し、`run-user-tests` で実操作中に直接測る。

画像で確認できないinteraction条件を `PASS` に含めない。許可された操作・観測channelがなければ `BLOCKED` または未確認と明記する。visual verifyのPASSを、利用者journey全体のPASSへ読み替えない。

## ステップ1: 変更の種類を分類する

変更内容から「何を確認すべきか」を決める：

| 変更の種類 | 確認手段 |
|---|---|
| Web UI (ブラウザ) | スクリーンショット / GIF（Chrome MCP） |
| ユーザー所有の Codex MCP App / Codex 連携 UI | 隔離した Codex Desktop を computer-use で公開入口から実操作 |
| デスクトップアプリ / TUI | スクリーンショット / GIF（computer-use） |
| Excel / PDF / 画像生成 | ファイルを開いて内容確認 + スクリーンショット |
| CLI / サーバー | ターミナル出力をキャプチャ（Bash）|
| 外部API呼び出し | 実レスポンスをキャプチャ |

## ステップ2: 起動方法を確認・記憶する

### 記憶があれば使う

プロジェクトのメモリ（`.Codex/` や `AGENTS.md`）に起動コマンドが記載されていれば使う。

### なければ自動検出する

```bash
# Web フロントエンド
cat package.json | python3 -c "import sys,json; d=json.load(sys.stdin); print(d.get('scripts',{}))"

# Python
cat Makefile 2>/dev/null | grep -A1 "^dev\|^run\|^start"
cat pyproject.toml 2>/dev/null | grep -A3 "\[tool\."

# Docker
ls docker-compose*.yml 2>/dev/null
```

### 起動方法をメモリに保存する（初回のみ）

起動コマンドが確定したら、次回以降のセッションで使えるようにメモリに保存する：

```
プロジェクト: <リポジトリ名 or ディレクトリ名>
起動コマンド: <コマンド>
URL: <http://localhost:XXXX>
備考: <特記事項があれば>
```

### アプリを起動する

- すでに動いているポートがあれば再起動不要
- バックグラウンドで起動し、ready になるまで待つ（最大30秒）

```bash
# ポート確認
lsof -i :3000 2>/dev/null | grep LISTEN
```

## ステップ3: 変更箇所を操作して証拠を撮る

### Web UI の場合（Chrome MCP 優先）

```
mcp__Claude_in_Chrome__navigate → 対象ページへ
mcp__Claude_in_Chrome__find → 変更された要素を特定
mcp__Claude_in_Chrome__form_input / left_click → 操作
mcp__Claude_in_Chrome__read_page → 内容確認
```

インタラクションがある場合（アニメーション・状態変化）は GIF を撮る：
```
mcp__Claude_in_Chrome__gif_creator
```

### ユーザー所有の Codex MCP App / Codex 連携 UI の場合

Codex 向け MCP App や Codex と連携する UI を実装・修正した場合は、**通常利用中の Codex とは別に隔離した Codex Desktop を computer-use で公開入口から実操作することを、標準の完了条件かつ推奨経路とする。** 公開されたボタン、入力、画面遷移、focus、結果を直接観測し、CTA が反応しなければ FAIL とする。

native opener で対象 URL を直接開くこと、単体テストだけ、静止画だけを、この実操作の E2E 代替にしない。通常利用中の Codex の会話やユーザーデータは操作しない。computer-use plugin が定める禁止事項・確認事項・許可境界を上書きせず、必要な確認に従う。

### デスクトップアプリ / TUI の場合（computer-use）

```
mcp__computer-use__request_access → アプリ名を指定
mcp__computer-use__screenshot → 現状確認
mcp__computer-use__left_click / type → 操作
mcp__computer-use__screenshot → 変更後の状態
```

複数ステップの操作は `computer_batch` でまとめる。

### Excel / PDF の場合

```bash
open /path/to/output.xlsx
sleep 3
```
その後 computer-use でスクリーンショット。
セル値・レイアウト・フォーマットを確認する。

### CLI / API の場合

```bash
# 実際のコマンドを実行してキャプチャ
<command> 2>&1 | tee /tmp/verify_output.txt
```

## ステップ4: コンテキストフリーなサブエージェントに認識させる

スクリーンショット・GIF・出力ファイルが得られたら、**このセッションの文脈を持たないサブエージェント**に認識させる。
これにより「期待しているから OK に見える」バイアスを排除する。

Agent ツールでサブエージェントを起動する際のプロンプトテンプレート：

```
以下のスクリーンショット（またはファイル）を見て、チェック項目を確認してください。
あなたはこの実装の経緯を知りません。画面に写っていること・いないことだけを根拠に答えてください。

## チェック項目
<変更内容から導いた具体的なチェックリスト>
例:
- [ ] ボタンが画面上に存在するか
- [ ] 操作前後の画像でモーダルの表示状態が変わったか（クリック回数や因果は操作logで別途確認）
- [ ] エラーメッセージが表示されていないか
- [ ] <具体的な値・テキスト> が表示されているか

## 判定
各項目について OK / NG / 不明 で答え、根拠を1行で書いてください。
最後に総合判定（PASS / FAIL / NEEDS_REVIEW）を出してください。
```

サブエージェントの判定が **FAIL** または **NEEDS_REVIEW** なら → ステップ5へ。
**PASS** なら → ステップ6のレポートへ。

## ステップ5: NGなら修正してサイクルを回す

サブエージェントの判定が FAIL / NEEDS_REVIEW の場合：

1. サブエージェントの根拠から原因を特定する
2. 実装を修正する
3. ステップ2〜4を繰り返す（アプリの再起動が必要なら再起動する）
4. 全チェック項目が PASS になるまで続ける

**「NG でした、修正が必要です」で終わらない。自分で直せるものは直してから報告する。**

## ステップ6: 証拠をレポートにまとめる

ユーザーがセッション上で見るだけで判断できる形にする。

```
## Visual Verify: <何を確認したか1行>

### 確認環境
- アプリ起動: <コマンドとURL>
- 確認手段: <Chrome MCP / computer-use / Bash>

### チェック項目と結果（サブエージェント判定）
| 項目 | 判定 | 根拠 |
|------|------|------|
| <項目1> | ✅ OK | <根拠> |
| <項目2> | ✅ OK | <根拠> |

### 証拠
<スクリーンショット・GIF・出力を貼る。ファイルパスだけでなくインラインで見えるようにする>

### Verdict: PASS | FAIL | BLOCKED
```

- **PASS**: 全チェック項目がサブエージェント判定で OK
- **FAIL**: 修正を試みたが解決できない問題が残っている（内容と現状を明記）
- **BLOCKED**: アプリが起動できない、ツールが使えないなど（理由と回避策の提案を明記）

## 注意事項

- **証拠はインラインで。** ファイルパスだけでは読者が開きに行く手間が発生する。スクリーンショットは必ずセッションに貼る。
- **GIF は動きがある操作に限定。** 静的な確認にはスクリーンショットで十分。
- **interactionを画像だけで証明しない。** 操作数、scroll数、自動遷移、focus、時間は実操作logまたは対象を直接読めるchannelで測る。
- **サブエージェントへの依頼は具体的に。** 「確認してください」では不十分。チェック項目を箇条書きで渡す。
- **環境セットアップに積極的に投資する。** `verifier-<project>.sh` などの起動スクリプトを作ってリポジトリに残すとリポジトリを跨いで再利用できる。
