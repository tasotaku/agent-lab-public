# Write for Readers

広く集めた情報を、読者の目的に必要な形へ編集する。短さではなく、読者が最小の負担で正確に判断・行動できることを優先する。

作業開始時に [references/learned-rules.md](references/learned-rules.md) を必ず読む。運用で確認された追加ルールを今回の手順にも適用する。

## 最初に作業の種類を決める

- **新規作成**: 素材から別の読者向け文書を作る。
- **書き直し**: 元文書の事実を保ち、目的・構成・語彙を直す。
- **レビュー**: 問題と修正案だけを返し、本文は変更しない。

元文書が長くても、元文書自体を短くすべきとは限らない。詳しい参照資料として残し、別の読者向け文書を作る選択を優先する。

## 1. 受け手を調べ、読後の行動を定める

依頼者と実際の受け手を分ける。依頼者について持っている知識を、別の受け手へ流用しない。

次の順で、受け手について集める。

1. 現在の会話にある、受け手本人の質問・訂正・使った用語を探す。
2. 許可された過去のやり取り、既存資料、会議記録、コメント、受け手本人の作成物を確認する。
3. 主な受け手、今回の利用場面、読後に求める判断・行動、読める時間を確認する。
4. 不明点によって冒頭の説明、用語、詳しさ、求める行動が変わるなら、残る不足だけを質問する。

資料を送付済み、会議へ出席済みという事実だけで、本人が理解・記憶しているとみなさない。役職だけから知識を決めない。
受け手本人への連絡は、ユーザーが許可した場合だけ行う。

執筆前に、次を簡潔に明示する。不明な欄を推測で埋めない。

```text
主な受け手:
確認できた知識・疑問:
推定していること:
不明なこと:
読後にしてほしい行動:
文書の種類:
本文で扱う範囲:
扱わない範囲:
```

「理解する」「知る」で止めない。何を選ぶ、承認する、実行する、質問するための理解かを書く。

会話・素材・既存文書から確認できる場合はそのまま進む。推定は事実として扱わない。不明点で成果物が大きく変わる場合だけ質問する。ユーザーに掲載内容の選別や受け手調査を丸投げしない。

読者と読後の行動が両方とも不明な場合は、「共有用の概要」などを勝手に設定して書き始めない。「誰が読み、読後に何を決める・実行する文書ですか」と一つの質問にまとめて確認する。

## 2. 文書の種類を一つ選ぶ

主な目的を一つにする。説明、判断、手順、参照を同じ重さで混ぜない。

- 判断・提案: 選択、承認、合意を助ける
- 説明・概要: 全体像や理由をつかませる
- 報告: 起きたこと、影響、次の対応を共有する
- 手順: 一つの作業を完了させる
- 参照・FAQ: 必要な事実を後から探せるようにする

各種類の構成は [references/document-patterns.md](references/document-patterns.md) の該当箇所だけを読む。

## 3. 素材を本文・詳細・不使用に分ける

各情報を次の基準で仕分ける。

### 本文に残す

- なくすと読者の判断・行動が変わる
- なくすと主張を誤解する
- 次の節を理解する前提になる
- 結論の信頼性を支える最小限の根拠である

### 詳細へ移す

- 必要な人だけが確認する根拠、例外、全件表、定義、出典
- 結論を変えないが、監査や再確認には必要な情報
- 読者の主な目的とは別の問いへの回答

付録、別文書、脚注、元資料へのリンクのうち、読者が必要時にたどれる方法を選ぶ。

### 使わない

- 読者の目的に関係しない周辺情報
- 同じ主張を繰り返す別の例
- 読者が当然知っていて、判断にも影響しない説明

削ることと、事実を隠すことを混同しない。不確実性、重要な反証、条件、リスクは本文に残す。

## 4. 本文より先に構成を作る

- 一つの見出しで、読者の一つの疑問に答える。
- 読者が必要とする順に並べる。調査した順、ファイルの順、思いついた順を使わない。
- 冒頭だけで、何の文書か、主な結論、読者に求めることが分かるようにする。
- 新しい話の枝を本文で育てない。主目的に必要なら構成へ昇格し、不要なら詳細へ移す。
- 長さやページ数は制約として扱い、品質の指標にはしない。

## 5. 読者の言葉で書く

- 一文では一つのことだけを言う。
- 一段落には一つの役割だけを持たせる。
- 結論、理由、具体例の順を基本にする。
- 抽象的な説明には、素材中の実例を一つ添える。
- 一つの概念には一つの呼び名を使い、途中で言い換えない。
- 読者が知らない専門用語は、可能なら日常語に置き換える。
- 正式名称が必要なら、日常語を先に書き、正式名称を括弧で添える。
- 組織をまたぐ読者に、素材を作った組織の社内名・部署名・システム名を既知扱いしない。初出で役割を説明するか、日常語だけで書く。
- 略語は、本文で繰り返し使う必要がある場合だけ導入する。
- 短い判断用文書では、用語集を先に覚えさせない。
- 長い参照資料では、検索のための用語集を置いてよい。ただし本文を理解する必須条件にしない。

### 識別子は、それが使われている理由に置き換える

コード番号、部署名、資料名、桁数のような識別子は、読者に「これは何の仲間か」を推測させる。
**識別子を消して、そのまとまりが何で選ばれているかを書く。** 文字数は減り、伝わる情報は増える。

- ✕ 502・503・508・524・525・526・527 → ○ 組織で決まる科目
- ✕ 附帯事業120〜126・事業外130・建設仮勘定141〜151 → ○ 電気事業以外の設備
- ✕ 固定資産側の科目3桁を費用項に変換 101水力→01 / 102汽力→02 → ○ 設備の種類を、どの事業のためかに変換

置き換えてよいのは、読者がその識別子で何かを引かない場合だけである。
読者が実際にそのコードを検索・入力・照合する文書では、識別子を残す。

### 数はそのまま書く

**識別子は抽象にしてよいが、数は抽象にしない。** 丸めると読者は「だいたい」しか受け取れず、
判断の根拠にできない。「半分弱」「数か所」「大半」「かなり」と書きたくなったら、実際の数を書く。

- ✕ 全体の半分弱 → ○ 66のうち30
- ✕ 大半の部署はここで決まる → ○ 334部署のうち320
- ✕ 精度は低い → ○ 測っていない（測っていないことと、低いことは違う）

数を書くために集計が必要なら、目で数えずスクリプトで出す。手で数えた値は外れる。

### 図の中の文字も本文と同じ規則で扱う

図を流用すると、ラベルは前の読者向けのまま残る。**本文だけ直して図を素通りさせると、
図が文書で最も具体的な部分になり、読者はそこで止まる。** ノード名・矢印のラベルも本文と同じ基準で直す。

同じ図を短い版と詳しい版で使うときは、ノードと矢印の対応を保ってラベルだけ変える。
形がずれると2つの版が別のことを言い出すので、機械的に照合できる形にしておく。

## 6. 根拠との対応を保つ

- 事実、推定、未確認を区別する。
- 数字、固有名詞、条件、引用、重要な例外を元資料と照合する。
- 圧縮により意味が強くなったり、確度が上がったりしていないか確認する。
- 本文から詳細を外した場合も、元資料へ戻れる参照を残す。
- 素材にない結論を補う場合は、推定と明示する。

## 7. 2回に分けて検査する

### 目的の検査

- 読者と読後の行動が冒頭から分かるか
- 各節が読後の行動に必要か
- 結論を変えない枝が本文に残っていないか
- 読者が次に何をすればよいか分かるか

### 前提と言葉の検査

判断を求める文書、対外文書、専門情報を含む文書では、利用可能なら必ず、会話や素材を渡していない独立した別エージェントに本文だけを読ませ、次を答えさせる。それ以外の短い文書でも、誤解の影響が大きければ同じ検査を行う。

```text
1. この文書は誰に、何をしてほしい文書か
2. 主な結論は何か
3. 意味が文中で立っていない語は何か
4. 飛んでいる前提や論理は何か
5. 判断・行動に足りない情報は何か
```

指摘をそのまま増補せず、説明を足すか、その話を削るかを選ぶ。独立した検査を黙って省略しない。使えない場合は同じ観点で検査し、独立した初見検査と実際の読者による確認が未実施であることを伝える。

修正後に、誤字、脱字、文法、数字の整合、見出しと本文の対応を機械的に見直す。

重要な文書では、公開前に想定読者へ口頭補足なしで読んでもらう。主な結論、求められた行動、止まった語を尋ね、意図と違えば文書を直す。

## 8. 成果を渡す

本文を先に渡す。その後に、必要な場合だけ次を短く報告する。

- 受け手について確認できたこと・推定・不明
- 読後の行動
- 詳細へ移した重要情報
- 元資料からは確定できなかった点
- 独立した初見検査を実施したか
- 初見検査で見つかり、修正した問題
- 実際の読者に確認してほしい質問

本文に編集過程や自己評価を混ぜない。文書ファイルを作る依頼では、既存の文書・スライド・表計算などの作成スキルと併用し、このスキルは内容設計を担当する。

## 運用から自動で改善する

セッション終了時の仕組みが、このスキルの実利用後に出た訂正・聞き返し・初見検査・ユーザーの編集差分を確認する。
別案件にも効く強い証拠がある場合だけ、[references/learned-rules.md](references/learned-rules.md) を自動更新する。

苦情が無いことを成功の証拠にしない。案件固有の事実や一度だけの好みを一般化しない。スキルの目的・発動範囲・権限を
変える必要がある問題は自動修正せず、設計相談へ回す。
