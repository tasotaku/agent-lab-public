# 独立利用者テストで改善する

実装担当として、固定済みの利用者テストでproduct findingがなくなるまで修正と再確認を繰り返す。実装担当がテストを設計・実行・合格判定しない。

## 実装前に利用者目標を確定する

最初に、ユーザーの目標、公開入口、想定利用者、対象viewportやOSなどの利用条件を確認する。ユーザーが示した具体条件はそのまま保持する。例は「すべての表示が1画面に収まる」「初期画面から3クリック以内」「開始後2秒以内にCodexが前面へ移り、手動切替は0回」。

利用者目標や公開入口が不明で合理的に推定できない場合だけユーザーへ聞く。テスト手順、採点方法、監査方法は聞かない。クリック数やscroll数など適切な観測項目は独立design担当に決めさせる。ユーザーの言葉を勝手に一般的な品質基準へ置き換えたり、失敗後に緩めたりしない。

## 固定specを先に作る

互換性のある固定specとlockがあれば再利用する。公開目標・入口・利用条件が変わった、または存在しない場合は `design-user-tests` を使い、freshなcontext-free design担当に実装前の代表journeyを書かせてlockする。

UIやcross-surface flowでは、利用者目標に関係するクリック／タップ／キー操作数、手動surface切替数、自動遷移と期限、focus・前面状態、初期viewport、scroll数を客観条件として固定する。すべてを少なくするのではなく、期待する通常経路を対象にする。

## freshな独立担当に実行させる

`run-user-tests` を使い、実装に参加しておらずdesign担当とも異なるfreshなエージェントへ、次だけを渡す。

- 固定specとlock
- 利用者が使う公開入口
- 実行に不可欠な起動、許可された直接観測、安全な後片付け情報

実装時の会話、修正意図、既知の問題、前回の結果は渡さない。テスト担当は実際の入口から目的の最終状態まで1回だけ操作し、固定したinteractionを実行中に直接測る。スクリーンショットや内部処理の成功から操作回数・自動遷移・focusを推測させない。製品やspecは編集させない。必須条件を直接観測できなければPASSではなく `NOT_RUN` または `INCOMPLETE` とする。

## 修正と再確認を繰り返す

product findingがあれば実装担当が製品だけを修正する。次は前回の結果を知らない別のfreshなエージェントへ、同じ固定specとlockを渡して再実行させる。

reportのproduct findingが0件で、必須条件に `NOT_RUN` / `INCOMPLETE` / blind spotがなくなるまで続ける。真の `TEST_SPEC_ISSUE` だけは `design-user-tests` のrevision手順で別のfresh design担当に次versionを作らせる。製品が通らないという理由でspecを緩めない。新しい製品要件の判断、権限、外部状態の変更が必要な時だけ、未達の条件と必要な判断をユーザーへ返す。

終了時は、固定specの場所とversion、達成条件ごとの最終実測、主な修正だけを簡潔に報告する。
